# Theme Lab Philosophy

## Professional tools should remain approachable

Theme Lab should help an administrator make coherent design decisions without requiring mastery of every Curve2 selector. Simplicity should come from good structure and defaults, not from hiding the consequences of choices.

## One project, one coherent design state

Every Studio edits part of the same project. The preview and compiler must combine those parts consistently rather than treating each screen as an isolated demo.

## Stability before novelty

A smaller feature that installs, upgrades, saves, previews, and rolls back reliably is more valuable than a larger feature that risks the forum. Development should proceed in reversible increments.

## Generated output should be understandable

Themes produced by Theme Lab should remain normal SMF themes. Their files should be readable, maintainable, and usable without a permanent runtime dependency on Theme Lab.

## Documentation is part of the product

Architecture, stored data, release behavior, and limitations should be written down. Documentation must be honest about what exists and what is only planned.

## Compatibility deserves deliberate work

SMF versions, existing projects, stored keys, integration hooks, package IDs, and generated output create contracts. Those contracts should change only with explicit reasoning, testing, and changelog coverage.
